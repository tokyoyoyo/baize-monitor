## 开发工作流

### 标准开发流程

1. **拉取代码**
   ```bash
   git checkout develop
   git pull origin develop
   ```

2. **创建特性分支**
   ```bash
   git checkout -b feature/your-feature-name
   ```

3. **开发功能**
   - 编写代码
   - 格式化代码：`make fmt`
   - 检查格式：`make fmt-check`
   - 运行测试：`make test-sequential`

4. **提交代码**
   ```bash
   git add .
   git commit -m "feat(module): description"
   ```

5. **推送代码**
   ```bash
   git push origin feature/your-feature-name
   ```

6. **创建 Pull Request**
   - 在 GitHub 上创建 PR
   - 等待代码审查
   - 根据审查意见修改

7. **合并代码**
   - PR 通过后合并到 develop 分支

### Makefile 工作流

```bash
# 开发前准备
make deps          # 下载依赖
make fmt           # 格式化代码

# 开发中
make build-agent   # 构建 Agent
make build-server  # 构建 Server

# 提交前检查
make fmt-check     # 检查代码格式
make tidy          # 清理依赖
make test-sequential  # 运行测试（避免数据库争用）

# 生成覆盖率报告
make test-coverage
```

## 数据库与 DTO 规范

### 数据库设计原则

1. **使用 GORM 管理数据库**
   - 通过 GORM struct tag 定义字段和索引
   - 使用 `gorm:"index"` 自动创建索引
   - 使用 `gorm:"uniqueIndex"` 创建唯一索引
   - 无需手动执行 SQL 创建索引

2. **JSONB 灵活存储**
   - 使用 JSONB 存储映射配置、变量映射等灵活结构
   - 支持复杂数据结构的完整保存
   - 新增字段无需修改表结构

3. **软删除支持**
   - 使用 `is_deleted` 字段支持数据软删除
   - 保留历史数据，便于审计和恢复

4. **时间戳追踪**
   - 使用 `created_at`、`updated_at` 追踪数据变更
   - GORM 自动维护这些字段

5. **枚举值标准化**
   - 使用字符串枚举而非数字，提高可读性
   - 便于新增枚举值

### DTO 设计原则

1. **请求验证**
   - 使用 `binding` 标签进行参数验证
   - 必填字段和可选字段明确区分

2. **指针可选**
   - 使用指针类型表示可选字段
   - nil 表示不使用该过滤条件

3. **分页统一**
   - 所有列表查询使用统一的分页参数结构

4. **响应标准化**
   - 使用统一的响应结构，包含分页信息

5. **版本兼容**
   - DTO 结构独立于数据库模型
   - 支持 API 版本演进

### 索引设计原则

**项目使用 GORM 的 `index` tag 自动管理索引**：

```go
// 基本单列索引（项目标准方式）
TargetIP string `gorm:"column:target_ip;size:45;index;not null"`

// 带类型的索引（PostgreSQL inet 类型）
TargetIP net.IP `gorm:"column:target_ip;type:inet;index;not null"`

// 唯一索引
Username string `gorm:"uniqueIndex;not null"`

// 时间字段索引
CreatedAt time.Time `gorm:"index"`

// 状态字段索引
Status string `gorm:"size:50;index"`
```

**索引命名规则**：
- GORM 自动生成：`idx_<表名>_<字段名>`
- 示例：`idx_alerts_parser_id`, `idx_hardware_info_target_ip`

**项目当前索引策略**：
- ✅ 使用 **单列索引**（Single-Column Index）
- ✅ 通过 GORM `index` tag 自动创建
- ✅ 索引类型：B-tree（默认）
- ❌ 暂无联合索引需求

**如需添加联合索引**（未来需求）：
```go
// 方式 1：使用相同索引名称创建联合索引
AlertStatus string    `gorm:"size:50;index:idx_status_time"`
AlertTime   time.Time `gorm:"index:idx_status_time"`

// 方式 2：使用 migrate 手动创建
func (Alert) Migrate(db *gorm.DB) error {
    return db.Exec("CREATE INDEX idx_alerts_status_time ON alerts(alert_status, alert_time)").Error
}
```

**最佳实践**：
1. 常用查询字段添加 `index` tag
2. 外键字段必须添加 `index` tag
3. 时间范围查询字段添加 `index` tag
4. 状态枚举字段添加 `index` tag
5. 避免过度索引（影响写入性能）

### 最佳实践

**查询优化**：
- 使用复合索引覆盖常用查询组合
- 对 JSONB 字段使用 GIN 索引支持复杂查询
- 时间范围查询使用时区一致的 UTC 时间
- 大数据量表考虑分区策略

**数据一致性**：
- 使用事务保证关联数据的一致性
- 外键关系在应用层维护（Go 语言特性）
- 定期清理过期数据（根据业务需求配置保留策略）

**扩展性考虑**：
- JSONB 字段支持新字段无需修改表结构
- DTO 与模型分离，支持 API 演进
- 枚举值使用字符串，便于新增枚举值

## 代码风格

### Go 代码风格

- **遵循 Go 官方风格**：使用 `go fmt` 格式化代码
- **使用 Makefile**：推荐 `make fmt` 和 `make fmt-check`
- **缩进**：使用 Tab（go fmt 默认）
- **行长度**：每行不超过 120 字符
- **命名规范**：
  - 包名：小写字母，简短有意义
  - 变量名：驼峰命名，局部变量可用简短名称
  - 函数名：驼峰命名，首字母大写表示可导出
  - 类型名：驼峰命名，首字母大写表示可导出
  - 常量名：全大写，单词间用下划线分隔

### 注释规范

- **包注释**：每个包都应该有包注释，说明包的功能
- **函数注释**：每个导出函数都应该有函数注释，说明函数的功能、参数和返回值
- **变量注释**：对于复杂的变量，应该添加注释说明其用途
- **代码注释**：对于复杂的代码逻辑，应该添加注释说明

### 错误处理

- **错误返回**：函数应该返回错误，而不是使用 panic
- **错误检查**：所有错误都应该被检查和处理
- **错误包装**：使用 `fmt.Errorf` 包装错误，添加上下文信息
- **错误类型**：对于可预期的错误，应该定义错误类型

### 测试规范

- **测试文件**：测试文件应该以 `_test.go` 结尾
- **测试函数**：测试函数应该以 `Test` 开头
- **测试覆盖**：尽量提高测试覆盖率，关键功能应该有单元测试
- **测试命名**：测试函数应该清晰地表达测试的内容
- **运行测试**：使用 `make test-sequential` 顺序运行测试（避免数据库争用）

## 目录结构规范

### 项目结构

- **cmd/**：命令行工具（如：cmd/agent）
- **internal/**：内部代码，不对外暴露（如：internal/agent, internal/server）
- **pkg/**：可被外部引用的代码（如：pkg/dto, pkg/models）
- **config/**：配置文件（如：config/agent.yaml）
- **doc/**：文档（如：doc/development/architecture）
- **deployments/**：部署配置（如：deployments/agent, deployments/server）

### 内部结构

- **按功能划分**：每个功能模块应该有自己的目录
- **分层结构**：
  - handler：处理 HTTP 请求
  - service：业务逻辑
  - repository：数据访问
  - model：数据模型

## 版本控制规范

### Git 规范

- **分支管理**：
  - `main`：主分支，稳定版本
  - `develop`：开发分支，集成新功能
  - `feature/*`：特性分支，开发新功能
  - `bugfix/*`：修复分支，修复 bug
  - `release/*`：发布分支，准备发布

- **提交规范**：
  - 提交信息应该清晰、简洁
  - 提交信息应该包含：
    - 类型：feat（新功能）、fix（修复）、docs（文档）、style（风格）、refactor（重构）、test（测试）、chore（构建）
    - 范围：影响的模块
    - 描述：简短的描述
    - 详细信息：可选，更详细的描述

  示例：
  ```
  feat(agent): 添加 CPU 温度监控功能
  
  添加 CPU 温度监控功能，支持读取 CPU 温度并发送到服务器
  ```

- **代码审查**：
  - 所有代码都应该经过代码审查
  - 代码审查应该关注：
    - 代码风格
    - 错误处理
    - 性能问题
    - 安全问题
    - 逻辑正确性

## 开发流程

### 开发步骤

1. **需求分析**：了解需求，分析系统架构和设计
2. **环境搭建**：搭建开发环境，配置依赖
3. **代码开发**：按照开发规范编写代码
4. **测试**：编写测试用例，进行单元测试和集成测试
5. **代码审查**：提交代码审查，确保代码质量
6. **部署**：部署到测试环境，进行功能验证
7. **发布**：发布到生产环境

### 代码审查流程

1. **创建 Pull Request**：开发者创建 Pull Request
2. **代码审查**：reviewer 审查代码
3. **修改代码**：开发者根据审查意见修改代码
4. **合并代码**：代码审查通过后，合并到目标分支

### 发布流程

1. **创建发布分支**：从 develop 分支创建 release 分支
2. **版本号**：更新版本号
3. **测试**：进行全面测试
4. **发布**：发布到生产环境
5. **合并**：将 release 分支合并到 main 和 develop 分支

## 性能规范

### 代码性能

- **避免不必要的分配**：尽量使用值类型，避免频繁的内存分配
- **避免循环中的重复计算**：将重复计算的结果缓存
- **使用适当的数据结构**：根据场景选择合适的数据结构
- **并发处理**：对于 CPU 密集型任务，使用 goroutine 并发处理

### 网络性能

- **减少网络请求**：合并多个请求，减少网络往返
- **使用缓存**：缓存频繁访问的数据
- **压缩数据**：对于大数据传输，使用压缩
- **连接池**：使用连接池管理数据库和网络连接

### 数据库性能

- **索引**：为查询字段创建索引
- **批量操作**：使用批量操作减少数据库往返
- **事务**：合理使用事务，避免长事务
- **查询优化**：优化 SQL 查询，避免全表扫描

## 安全规范

### 输入验证

- **验证所有输入**：对所有用户输入进行验证
- **参数检查**：检查参数的类型、长度、范围等
- **防止 SQL 注入**：使用参数化查询，避免拼接 SQL
- **防止 XSS 攻击**：对输出进行 HTML 转义

### 认证和授权

- **使用 JWT**：使用 JWT 进行认证
- **密码存储**：使用 bcrypt 等安全算法存储密码
- **权限检查**：对每个请求进行权限检查
- **最小权限原则**：只授予必要的权限

### 数据保护

- **加密传输**：使用 HTTPS 加密传输数据
- **敏感数据**：敏感数据应该加密存储
- **日志安全**：日志中不应该包含敏感信息
- **备份**：定期备份数据

### 依赖安全

- **依赖管理**：使用 go mod 管理依赖
- **依赖检查**：定期检查依赖的安全漏洞
- **版本锁定**：锁定依赖版本，避免意外升级
